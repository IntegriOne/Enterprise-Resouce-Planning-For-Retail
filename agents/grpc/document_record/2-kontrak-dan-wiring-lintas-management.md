# Kontrak DRM dan wiring di kedua sisi

Gunakan dokumen ini bersama [inventaris GraphQL dan RPC](1-inventaris-operasi-dokumen-dan-record.md) dan [instruksi pelaksanaan](../../instructions/document_record/1-leader-implementasi-grpc-gateway-dan-integrasi-dokumen-instructions.md). Path menunjuk checkout saat penyusunan. File dan RPC yang perlu dibuat disebut sebagai **usulan**.

## Kontrak pemilik dokumen

1. Owner menyediakan pemeriksaan privat untuk `create/upload/link/publish/read/revoke/dispose` yang relevan. Input mengikat identitas workload, audience, actor dari IAM, legal entity, purpose, jenis/ID sumber, revisi sumber, subject atau party, tipe dokumen dan versi yang sedang diperiksa. Keluaran memuat keputusan, binding persis, versi keputusan dan expiry. Owner memeriksa sumber otoritatifnya tanpa memanggil DRM lagi untuk keputusan yang sama. Cegah siklus DRM → owner → DRM dan confused deputy.
2. Simpan di DB owner minimal `document_id`, `document_version_id`, SHA-256 byte dan key revisi transaksi; simpan publication ref/issuer bila dipakai. Bedakan ID dokumen DRM, versi DRM, publikasi DRM, publikasi owner dan ID transaksi. Gunakan FK lokal saja. Untuk field lama berbentuk teks, sediakan pembacaan kompatibel, validasi/verifikasi sebelum backfill, karantina ref ambigu, lalu alihkan writer; larang resolusi diam-diam ke versi terbaru.
3. Owner menyimpan intent/outbox bersama transaksi sumber. Renderer owner membuat file dari snapshot immutable dan versi template/font. DRM memproses upload, scan, sealing dan declaration. Owner mengonfirmasi versi/digest dan penerbitan bisnis; DRM mempublikasikan versi itu ke penerima dari owner. State `available` hanya membuktikan file tersedia. Assertion dan key stabil per artefak, misalnya entity + management + resource + source revision + logical artifact + purpose. Koreksi substansi menghasilkan versi atau artefak koreksi tersendiri.
4. Producer → inbox DRM dan outbox DRM → inbox owner menggunakan mTLS dan allowlist per jenis event. Envelope minimal berisi event ID, producer, schema version, entity, aggregate/version, sumber/revisi, reference artefak, correlation/causation dan digest tervalidasi. Gunakan outbox snapshot dan acknowledgement consumer setelah transaksi, dedup event ID **dan efek bisnis**, retry dengan lease, deteksi out-of-order/gap, DLQ serta rekonsiliasi melalui lookup owner. Batasi distribusi digest dan subject ke consumer berwenang. Tanpa byte, nominal gaji, rekening, alamat, credential atau URL unduhan di event.
5. Route usulan dari DRM adalah `DocumentVersionAvailable` dan `DocumentVersionQuarantined` ke pemilik; `DocumentVersionPublished` dan `DocumentPublicationRevoked` ke owner dan proyeksi portal yang berwenang; `RecordDeclared`, `LegalHoldActivated`, `LegalHoldReleased` dan `DocumentDispositionCompleted` ke owner/audit yang perlu tahu. Cek producer/schema aktual sebelum publikasi. Buat client, handler inbox, port aplikasi, binding di `cmd`, CA/SAN/audience, config, Compose, worker dan ack pada **kedua service**. Berlangganan event tidak memberi hak baca. Pakai pemisahan identitas workload dan principal yang meminta tindakan.

### Slip gaji tanpa ketergantungan melingkar

1. Finance mengotorisasi penerbitan **run** lewat `PublishPayrollRun` (RPC `PublishPayroll` mode run) dan outbox `payroll.published` untuk aggregate `payroll_posting`. HRM memverifikasi run, posting/jurnal, entity, input/output digest dan ID penerbitan Finance sebelum merender. Transfer bank adalah status terpisah. HRM tidak memindahkan uang.
2. Suntikkan `PayslipStorage`, `PayslipDocumentReader`, dukungan `PayslipStorageRestorer.RestorePrivatePayslip`, font renderer yang sama dan Finance verifier pada `buildPayslipRegistryOptions`; wiring saat pemeriksaan hanya mengirim Finance verifier. Pertahankan `WithPayslipPublication`, `WithPayslipVerifier`, `WithPayslipReissue`. `StorePrivatePayslip` mengikat worker/result/entity/publication, key stabil dan digest. DRM scan+seal, declare record, lalu kembalikan versi persis. HRM menyimpan ref itu secara idempoten.
3. Untuk bukti per hasil, hubungkan `PublishPayroll` mode result dengan versi DRM dan digest PDF. Verifier Finance mencocokkan binding hasil/worker/run, bukan hanya kesamaan hash. Bedakan `payroll.payslip_published` per item dari `payroll.published` per run; callback per item tidak memicu render run lagi. Sepakati identitas run publication, publication item Finance serta DRM publication secara eksplisit dalam kontrak dan mapping data lama. Terbitkan DRM hanya untuk employee user yang ditetapkan HRM setelah bukti Finance yang tepat. Render tidak menunggu event item yang memerlukan file yang sedang dibuat.
4. Pertahankan `myPayslips`, `myPayslip`, `myPayslipPdf` dan `reissueEmployeePayslip` di Gateway HRM. Employee aktif dengan grant SELF dapat mengambil PDF miliknya. Mantan employee meminta **HR** dengan MFA dan scope entity. Jika PDF belum pernah terbentuk, render satu kali dari snapshot terbit. Jika metadata menyatakan byte fisik hilang dan masih boleh dipulihkan, restore versi logis lama dengan byte identik, generation fisik terverifikasi dan jejak repair append-only. Tombstone, salah digest, forbidden, unknown dan unavailable tidak memicu regenerasi. Koreksi payroll memakai versi/penerbitan baru dan keputusan Finance.
5. Uji kehilangan response setelah simpan DRM sebelum HRM/Finance mencatat ref, dua permintaan cetak ulang paralel, cetak tanpa PDF, blob hilang, revoked worker, hasil asing, serta perubahan template/font. Digest PDF berbeda dari digest snapshot kalkulasi. PDF lama dan akses berlakunya terjaga sesuai keputusan owner. ## Penyelesaian per jalur

Prioritaskan management yang ada di checkout dan kerjakan perubahan sisi pemilik sampai berjalan. Untuk layanan belum tersedia simpan kontrak, owner, field, route, syarat aktivasi dan kasus uji pada `agents/notes/document_record/`. Contoh Quality, Workforce, Planning, Workflow, Integration dan Manufacturing dalam dokumen logika dipetakan ke owner aktif yang sah bila fungsinya sudah ada. Management di luar 13 tetap memerlukan keputusan owner; Manufacturing tetap paused. Untuk tiap integrasi laporkan **didefinisikan → client/server terpasang → dua arah diuji → HTTPS terbukti**, lengkap dengan path, SHA, correlation tersanitasi serta bukti tidak terjadinya efek bisnis kedua.
