**Kesimpulan.** Posting payroll HR dan notifikasi alokasi pembayaran ke Procurement memiliki jalur implementasi. Dua risiko operasional terpisah adalah bukti valuasi WMS yang belum dikirim saat probe sukses dan event untuk publisher umum yang tidak terpilih saat relay Procurement aktif.

**Lingkup pemeriksaan.** Pembacaan statis checkout bersama pada 28 November 2026 WIB, HEAD `22bc75143003d6d745f386d9808eefb3c5c5c26c`, termasuk source lokal yang belum di-commit. Bukti runtime terdahulu disebut terpisah bila tersedia. Tidak dilakukan transaksi HTTPS, transfer, deployment atau perubahan aplikasi pada audit ini.

## Kecocokan dengan rancangan bisnis

Procurement §23 dan Inventory §19/22 memerlukan keterkaitan otorisasi PO, bukti accepted receipt atau jasa, invoice, payment, credit dan reversal. AP sudah menarik fakta PO dan receipt. Bridge WMS untuk valuasi belum mengirim efek. PLM §13/19 menetapkan item dan revisi sebagai referensi dan Finance pemilik nilai. Payout Xendit pada BuildApp memakai mode test dan resolver tujuan sandbox; bukti ini tidak menunjukkan pembayaran bank nyata. ## Temuan dan dampak

### FA-01 — P1 · Valuasi WMS tanpa pengiriman efek dan replay lintas item kurang ketat

Publisher WMS memanggil probe `IsValuationServiceReachable` dan mengembalikan sukses, tanpa mengirim event ke `ApplyInventoryCostEvent`. Finance memang memiliki RPC workload dan penyimpanan cost entry. Pada hit existing source/effect, service membandingkan kind, quantity dan value, lalu mengembalikan entry lama; item ID tidak ikut dibandingkan. Kesalahan lookup selain not-found juga tidak dipisahkan sebelum jalur pembuatan. Bukti receipt untuk matching AP adalah alur pull terpisah. ### FA-02 — P1 · Filter relay privat dapat menyisihkan tujuan webhook yang aktif

`buildOutboxRelay` membentuk publisher fallback log/webhook. Jika Procurement invoice relay diaktifkan, repo selalu diganti `ForPrivateInvoiceDelivery(hrmCloser != nil)`. Filter `SelectPendingBatchForUpdate` kemudian hanya mengklaim subset invoice/payment/credit dan, opsional, payroll. Event di luar subset tidak akan pernah sampai ke fallback lewat relay ini, walaupun fallback sudah dikonfigurasi. Pada mode standby privat saja, penyaringan tersebut justru menjaga event lain. ### FA-03 — P2 · Kredensial client EF tidak diteruskan dan binding respons longgar

Adapter EF sudah memiliki CertFile/KeyFile/CAFile/ServerName, tetapi `BuildAppWithDeps` mengisi target, timeout dan HMAC saja. `GetLegalEntity` serta `GetParty` memetakan ID dari argumen permintaan, sementara `ValidateOrganizationUnit` dan `ValidateLocation` hanya membaca is_active. Data yang berasal dari objek berbeda dapat terlihat seperti fakta target. ### FA-04 — P1 · Pemicu publikasi run dan identitas penerbit

Matriks Finance mengusulkan `publishPayrollRun` sebagai operasi bisnis dan menjaga `PublishPayroll` privat. SDL payroll Finance saat ini memiliki `reviewFinanceClearance` dan `completePayrollSettlement`. Handler privat sudah bisa menerbitkan satu run dan menghasilkan `payroll.published`; pada bootstrap dan pemanggil Go yang diperiksa, tidak ditemukan pemicu reguler Finance untuk memulai publikasi dari alur operator. Di `PublishPayrollRun`, bila principal pemanggil tidak dapat di-parse sebagai UUID, kode memakai UUID payroll run sebagai actor dalam audit. Identitas penerbit menjadi rancu untuk principal SPIFFE.
